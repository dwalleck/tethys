# Easier routes to compiler-backed C# parity for tethys

Research report, 2026-09-06. Scope: the maintainer's question "are there EASIER ways?" against the approved plan (tethys-07eh / tethys-rvr5: explicitly-granted two-stage host, evaluation-unit = project x TFM, separate grants, unique-or-decline, direct vs possible dispatch, day-one classic .NET Framework 4.8 support). Target repo: ~55 classic csproj + 17 vbproj, 1700 .cs / 380 .vb, ASP.NET Web Forms, packages.config, no SDK-style projects.

Every claim is tagged **[verified]** (primary source read, or reproduced locally) or **[inferred]** (reasoned from verified facts). Local probes ran on Linux (CachyOS), .NET SDK 10.0.102 (8.0.417 and 9.0.310 also installed), **no Mono, no msbuild.exe, no nuget.exe**, against a *generated* fixture under `/tmp/legacyprobe/` (classic net48 Web Forms csproj with packages.config + `Microsoft.WebApplication.targets` import + ProjectReference to a classic vbproj). No real repositories were touched. Probe transcript summary is in the appendix.

---

## Headline findings

1. **The whole legacy fixture compiles on Linux with the plain .NET SDK — no Mono, no Windows** — once three MSBuild properties are supplied: `VSToolsPath=` (neutralises the VS-only import), `CustomAfterMicrosoftCommonTargets=<Microsoft.NETFramework.ReferenceAssemblies.net48 .targets>`, `FrameworkPathOverride=<its .NETFramework/v4.8 dir>`. `dotnet build` succeeded for csproj *and* vbproj; Roslyn `MSBuildWorkspace` then produced a **0-error C# compilation with the VB project bound**. **[verified]** The blocker is not hosting; it is `packages.config` restore (see 3).
2. **Roslyn already ships the "out-of-process legacy host" the plan describes.** `Microsoft.CodeAnalysis.Workspaces.MSBuild` runs design-time builds in a separate BuildHost process (netcore / net472 / Mono), picks the host by inspecting the project XML, and falls back with a logged warning. Re-implementing "compiler-input acquisition + host qualification" in a tethys-owned adapter duplicates this. **[verified: source + PRs #69616, #70263, #70469]**
3. **`dotnet restore` cannot restore `packages.config`** — NuGet docs: "packages.config restore is only available with MSBuild 16.5+, and not with dotnet.exe"; reproduced ("Nothing to do") even with `-p:RestorePackagesConfig=true` and with the VS import neutralised. On Linux the only supported restorer is `nuget.exe` under Mono (which is what CodeQL does, and it no-ops without Mono). **[verified]** Implication: on Linux the restore grant is unsatisfiable for this repo unless `packages/` is already present (committed, or produced on Windows/Mono).
4. **scip-dotnet is a thin `MSBuildWorkspace` wrapper**, C# + VB, maintained (v0.2.14, 2026-05-05). Out of the box it **failed to load both fixture projects on Linux** (MSB4019 then "reference assemblies for .NETFramework,Version=v4.8 were not found") and wrote an empty 951-byte index; with the same three properties passed as environment variables plus a stub `Microsoft.WebApplication.targets` it indexed everything (11 KB). But its output is unsuitable as tethys's evidence format: no enclosing symbol / call edges, overloads disambiguated by *declaration-order ordinal* (`Describe(+1).`), definitions index-local by default so cross-language references do not join, generated documents skipped. **[verified]**
5. **Roslyn's LSIF generator is dead**: removed from `dotnet/roslyn` main on 2025-06-10 ("This experiment has been abandoned. Removing our code.") with final cleanup 2026-01-31; it was only ever published to the Azure `dotnet-tools` feed, never nuget.org. Its `--compiler-invocation` idea survives, better, in **`complog` (Basic.CompilerLog)**, which turns the user's own binlog into a portable file from which Roslyn `Compilation`s (C# and VB, references and generated files included) are rebuilt with **zero MSBuild/target execution by tethys**. Reproduced: C#→VB binding and doc-comment IDs recovered from a `.complog` in 27 lines. **[verified]**
6. **Doc-comment IDs are the right canonical identity** (spec-defined, overload-disambiguating, cross-tool; Roslyn's own LSIF monikers were `dotnet-xml-doc` = `<AssemblyName>#<DocCommentId>`). Verified coverage and the exact holes: locals → `null`; type parameters → `!:T`; lambdas → nameless `M:Type.(System.Int32)`; **local functions get an ID that omits the containing method, collides, and does not round-trip**. IDs are not assembly-qualified; tethys must key by (evaluation unit, id). **[verified]**
7. **"No cross-language binding / VB out of scope" makes compiler-backed parity impossible for the target repo as written.** C# projects that `ProjectReference` a vbproj cannot reach a confirmed compilation without VB metadata. `CSharpCompilation` rejects a `VisualBasicCompilationReference` (`ArgumentException`), but a **metadata-only emit of the VB compilation (3 KB) binds cleanly** — MSBuildWorkspace does exactly this ("skeleton" references) automatically. Minimum viable amendment: *bind C# → VB metadata; do not index VB source*. **[verified]**

## A. Off-the-shelf semantic indexers

### A1. Sourcegraph `scip-dotnet`

Pinned: repo `sourcegraph/scip-dotnet` main @ `47884461a7` (2026-05-27, "feat: add .slnx solution format support"), latest release **v0.2.14** (2026-05-05); csproj carries `<Version>0.2.15</Version>` unreleased; installed tool reports `0.2.14+3e1f671e65…`. 34 stars, Apache-2.0, `renovate.json` keeps deps current. Targets `net10.0;net9.0;net8.0`; depends on `Microsoft.Build.Locator 1.7.8`, `Microsoft.CodeAnalysis*.Workspaces 5.3.0`, `Microsoft.CodeAnalysis.Workspaces.MSBuild 5.3.0`. **[verified: ScipDotnet/ScipDotnet.csproj]**

- **Loader** [verified: `ScipDotnet/Program.cs`, `ScipProjectIndexer.cs`]: `MSBuildLocator.RegisterDefaults(); MSBuildWorkspace.Create()`; before opening it shells out `dotnet restore <sln> /p:EnableWindowsTargeting=true` (skippable with `--skip-dotnet-restore`, `--nuget-config-path`, `--dotnet-restore-timeout`), then `OpenSolutionAsync`/`OpenProjectAsync`. Accepts `.sln/.slnx/.csproj/.vbproj`. Multi-target: picks the `Project` whose name contains `(net{CurrentRuntimeMajor}.0)` else the first — one TFM only. No MSBuild property/host options exist on its CLI.
- **Classic non-SDK / .NET Framework / packages.config on Linux** [verified by run]: on the fixture, v0.2.14 logged `Failure: Msbuild failed when processing the file '…/LegacyWeb.csproj' … "…/sdk/10.0.102/Microsoft/VisualStudio/v18.0/WebApplications/Microsoft.WebApplication.targets" was not found` (MSB4019) and for the vbproj `Microsoft.Common.CurrentVersion.targets: (1259, 5): The reference assemblies for .NETFramework,Version=v4.8 were not found` (MSB3644), exit 0, `index.scip` = 951 bytes with zero documents. `dotnet restore` reported "Nothing to do" (packages.config ignored). Because MSBuild reads environment variables as properties, running it with `VSToolsPath=/tmp/legacyprobe/stubvs` (containing an empty `WebApplications/Microsoft.WebApplication.targets`), `CustomAfterMicrosoftCommonTargets=<refasm .targets>`, `FrameworkPathOverride=<v4.8 dir>` and a hand-populated `packages/` folder indexed all 8 documents in 1.3 s (11 213 bytes). The Docker image is `FROM mcr.microsoft.com/dotnet/sdk:10.0` — no Mono, so the same fallback applies in Docker **[inferred from Dockerfile]**. On Windows with VS/Build Tools installed, Roslyn would pick the net472 BuildHost and VS MSBuild, so the VS-only import resolves natively **[inferred from BuildHostProcessManager]**.
- **VB.NET** [verified: `ScipVisualBasicSyntaxWalker.cs`, issue #26 "Add Visual Basic support" closed 2023-05]: VB documents are indexed with the same symbol scheme.
- **Relationships emitted** [verified: `ScipDocumentIndexer.VisitOccurrence`]: for a named type definition, `is_implementation` to every ancestor `BaseType` (walked to the root, `System.Object/Enum/ValueType` suppressed) and to every entry of `AllInterfaces`; for a method definition, `is_implementation + is_reference` to each `OverriddenMethod` (chain) and to interface members it implements explicitly or implicitly (`FindImplementationForInterfaceMember`). No `is_type_definition`, no `enclosing_symbol`, no `enclosing_range`, no `symbol_roles` beyond Definition (Occurrence carries only `Symbol`, `SymbolRoles`, `Range`). **No call edges and no caller attribution** — SCIP has no call-graph concept; tethys would have to attribute reference occurrences to enclosing definitions by span containment against its own tree-sitter symbol spans **[inferred]**.
- **Symbol format** [verified: `ScipSymbol.cs`, decoded index]: `scip-dotnet nuget <AssemblyName> <AssemblyVersion> Ns/Type#member` with `. .` (index-local package) for anything with a source location unless `--allow-global-symbol-definitions`. Descriptor suffixes are non-standard in places: events get the *type* suffix (`Extras#Changed#`), indexers become the term `` `this[]`. ``, explicit implementations become a backticked full name (`` Extras#`LegacyWeb.Services.IShape.Area`(). ``), constructors `` `.ctor`(). ``. **Overloads are disambiguated by ordinal position among same-named members in declaration order**: `OrderService#Describe().` and `OrderService#Describe(+1).` — not by parameter types. Adding, removing or reordering an overload renames the others across the index. Locals, range variables, type parameters, local functions and anonymous symbols are `local N`.
- **Partial classes** [verified: decoded index]: each declaring file emits a definition occurrence and a `SymbolInformation` for the same symbol (the fixture's `_Default` appears twice, once per file) — fine for tethys.
- **Generated code / source generators** [verified: `ScipProjectIndexer.IndexProject` iterates `project.Documents` only]: generator outputs (`GetSourceGeneratedDocumentsAsync`) are never indexed; references *into* generated symbols appear as occurrences with no definition in the index. Note that `Project.GetCompilationAsync()` in the workspace layer still runs generators to build the compilation **[inferred from Roslyn CompilationTracker design]**.
- **Size / perf**: fixture 2 projects, 8 docs: 1.3 s, 11–13 KB. Third-party datapoint (samchon/compiler-graph#75, evaluating scip-dotnet for a code graph): Serilog cold run 20.5 s vs 25.1 s for csharp-ls; they concluded "Stock scip-dotnet omits enclosing attribution, kinds, diagnostics and role information required by the graph, and its relationships flatten transitive ancestry, and its identities have known namespace, generic arity, project/assembly and declaration-order problems" and chose a pinned MSBuildWorkspace sidecar instead **[verified quote; third-party judgement]**. No scip-dotnet issues about large-solution memory exist; the tracker (10 relevant of ~100 issues) is dominated by restore/Windows-targeting fixes.

**Verdict**: usable as an *oracle/cross-check* for occurrences and implementation relationships; **not** usable as tethys's Pass-3 evidence format (identity, enclosing attribution, direct-vs-dispatch, accessor effects and generated-input provenance are all absent).

## B. Symbol identity: documentation-comment IDs vs SCIP

**Specification** [verified: ECMA-334 Annex D ("informative"), MS Learn "XML documentation comments → ID strings", VB language spec "Documentation Comments → ID strings"]: `N:`/`T:`/`F:`/`P:`/`M:`/`E:` prefix; fully qualified name with `.` separators and `#` replacing `.` inside member names (`#ctor`, `#cctor`, explicit interface implementations); parameter list in `( )` encoded like a CLI signature (`System.String`, `System.Int32@` for by-ref, `*` pointer, `[]`, `[0:,0:]`); generic arity as `` Type`n ``, method arity `` Method``n ``, type-parameter references `` `i `` (type) / `` ``i `` (method); conversion operators append `~ReturnType`; indexers are `P:…Item(…)`. Return type and calling convention are deliberately excluded "because they aren't used to differentiate overloaded methods".

**Roslyn API** [verified: `src/Compilers/Core/Portable/DocumentationCommentId.cs`; MS Learn API pages for `ISymbol.GetDocumentationCommentId`, `DocumentationCommentId.CreateDeclarationId/CreateReferenceId/GetSymbolsForDeclarationId/GetFirstSymbolForDeclarationId`]: `ISymbol.GetDocumentationCommentId()` "Returns the Documentation Comment ID for the symbol, or null if the symbol doesn't support documentation comments"; `CreateDeclarationId` returns `null` when the generator fails; `GetSymbolsForDeclarationId(id, compilation)` resolves an ID back to symbols in a given compilation.

**Observed on the fixture (MSBuildWorkspace 5.3.0 / Roslyn 5.3.0)** [verified]:

Additional properties **[verified from source/spec]**: IDs are for *original definitions* — a constructed symbol (`List<int>.Add`) must be reduced via `OriginalDefinition` and the substitution recorded separately (matches plan Q20). IDs carry **no assembly/project qualification**: two evaluation units can legitimately declare the same `T:Foo.Bar` (InternalsVisibleTo forks, copied files), so tethys must key by (evaluation unit or assembly identity, doc-id) — exactly what Roslyn's LSIF did with `AssemblyName#`. Parameters have no ID (LSIF used `Asm#containerId#name`). Cross-tool: the same strings are what `csc /doc`, `vbc /doc`, DocFX, Sandcastle, `cref` resolution and Roslyn LSIF monikers use; stability across Roslyn versions is by spec (the format predates Roslyn).

**Comparison with SCIP for C#** [verified: `scip.proto` @ `1c2b6db7e560` grammar; scip-dotnet `ScipSymbol.cs`]: the SCIP grammar is `<scheme> ' ' <manager> ' ' <package-name> ' ' <version> ' ' (<descriptor>)+` with `<method> ::= <name> '(' (<method-disambiguator>)? ').'` where the disambiguator is any `<simple-identifier>` — the spec does not prescribe how to disambiguate. scip-dotnet chose a declaration-order ordinal (`Describe(+1).`), which is unstable under edits and not derivable from a signature; a tethys emitter could instead put a doc-ID-derived signature hash in that slot and remain a valid SCIP symbol. scip-dotnet's package component (assembly name + version, or `. .`) is the only assembly qualification and it is dropped for in-source symbols by default. Net: doc-comment IDs are strictly more precise and more stable than what scip-dotnet emits; SCIP is a fine *container* if tethys ever wants to export, but not a better identity.

**Recommendation for tethys identity**: `(evaluation_unit_id, doc_comment_id)` for every declaration Roslyn gives an ID to; synthesise stable local IDs of the form `<containerDocId>#local:<ordinal or span>` for lambdas, local functions, locals and parameters (Roslyn's own LSIF treated these as document-local). Never trust `GetDocumentationCommentId()` for `MethodKind.LocalFunction`/`AnonymousFunction` — verified collision.

- **MSBuildWorkspace does (b) automatically** [verified: `SolutionCompilationState.GetMetadataReferenceAsync` — "If same language then we can wrap the other project's compilation into a compilation reference … otherwise get a metadata only image reference that is built by emitting the metadata from the referenced project's compilation and re-importing it"; `SolutionCompilationState.SkeletonReferenceCache.cs` — "Skeletons are used … to allow cross-language project references with live semantic updating between VB/C# and vice versa"]. Caveat from the Roslyn comment: skeleton build fails on VB code with errors the VB compiler cannot recover from, in which case Roslyn "limp[s] along with stale data" — tethys must treat a failed skeleton as an Indeterminate input.
- **scip-dotnet** [verified]: indexes VB documents and C# references to VB symbols, but in default mode the C# side names the target `scip-dotnet nuget VbLib 0.0.0.0 VbLib/VbOrder#` (metadata symbol → package) while the VB definition is `scip-dotnet nuget . . VbLib/VbOrder#` — **the join is broken**; with `--allow-global-symbol-definitions` both sides are `VbLib 0.0.0.0 …` and join.
- **Roslyn LSIF generator**: same workspace mechanism; monikers are assembly-prefixed doc IDs, so the join works by construction **[inferred from `SymbolMoniker.Create`]**.
- **complog** [verified]: the VB and C# compilations are both present; the C# one references the real `VbLib.dll` the build produced; cross-language binding is native.
- **Assessment of the plan's "no cross-language binding / VB out of scope"**: for the target repo (C# → 17 vbproj) this rule means every C# project with a `ProjectReference` to a vbproj either (i) fails to compile (CS0246/CS0234 on every VB type — the "77 errors" state above) and can never be Confirmed, or (ii) silently drops those references, which the plan forbids. **Compiler-backed parity for this repo is therefore impossible under the rule as written.** The minimum amendment is: *VB projects are semantic inputs, not indexed sources* — bind C# references to VB metadata (skeleton or built assembly), record the VB unit's identity/provenance, and leave VB declarations/references unindexed (`Indeterminate` for VB-scoped queries). MSBuildWorkspace and complog give this for free; the direct-Roslyn design needs ~15 lines (build the `VisualBasicCompilation` from the VB unit's inputs, metadata-only emit). Note the distinction: the wayfinder's "mixed Rust/C# workspaces … without cross-language reference or call binding" is about Rust↔C#; C#→VB is a same-runtime, compiler-supported reference and should not be lumped with it **[inferred]**.

## E. Cost comparison

Requirements the approved plan imposes (from tethys-07eh/rvr5): explicit trust grant for MSBuild evaluation; separate grants for restore, design-time/target execution, analyzers, source generators; evaluation-unit identity = project × TFM owned by evaluation-only discovery; exact compiler inputs and provenance captured and reconciled against discovery before publication; no silent host/provider substitution or downgrade; per-unit Confirmed/Indeterminate with stable reasons; doc/identity rules from section B; direct-vs-possible dispatch; accessor effects.

### Option 1 — approved plan as written

- **New surface**: (a) tethys-owned out-of-proc MSBuild *acquisition* adapter that runs design-time targets and captures csc/vbc arguments per unit, with host selection/qualification for SDK vs classic (Windows VS MSBuild, Linux .NET SDK + reference-assembly profile, Mono?), error mapping to the standing reasons; (b) direct-Roslyn host that builds `CSharpCompilation` from explicit inputs and walks syntax/semantics into the plan's vocabulary; (c) VB metadata production if the rule is amended; (d) Rust ingestion (`strategy=roslyn` evidence, provenance, standing); (e) grants/config/CLI; (f) legacy fixtures and oracles.
- **What is duplicated**: (a) re-implements `ProjectBuildManager` + `ProjectFile`/`CSharpProjectFile`/`VisualBasicProjectFile` + `BuildHostProcessManager` (host kinds, fallbacks, Mono discovery, dotnet relaunch to match SDK) — roughly 3–5 k lines of Roslyn that Microsoft tests against VS, SDK and Mono layouts. The classic-on-Linux profile (section C) still has to be discovered and applied by tethys in either design, but the plan's version also has to *execute* the design-time build and parse `ProvideCommandLineArgs` output itself.
- **Rough size** [inferred]: adapter 1.5–3 k C# LOC + tests; Roslyn walker 1–2 k; Rust ingestion 1–2 k; grants/CLI 0.5 k; fixtures. The adapter is the riskiest part (host matrix, MSBuild API versioning, MSB error taxonomy) and the least differentiating.

### Option 2 — `MSBuildWorkspace` sidecar emitting doc-ID-keyed JSONL

- **Demonstrated**: 60 lines opened the solution with three global properties, produced a 0-error compilation, bound C#→VB, and printed doc IDs and per-call target identity. A production walker that emits declarations (with all locations), references with selected member + constructed substitutions + accessor effect, direct calls, implementation/override relationships, possible-dispatch candidates, and per-unit diagnostics is the *same* walker Option 1 needs — perhaps 0.8–1.5 k lines. The Rust ingestion is identical to Option 1.
- **What becomes unnecessary**: the tethys-owned acquisition adapter and host matrix (BuildHost does it), command-line capture/parsing (`Project.MetadataReferences`, `ParseOptions`, `CompilationOptions`, `Documents` are already materialised), multi-TFM fan-out (each TFM is a separate `Project`), VB skeletons (automatic), analyzer-reference plumbing.
- **What still applies, and how it maps**:
  - *Design-time target grant*: mandatory — MSBuildWorkspace always runs `Compile;CoreCompile` with `SkipCompilerExecution=true`; the sidecar must refuse to start without it. There is no evaluation-only mode; discovery must remain tethys's evaluation-only stage (already decided) and the sidecar's project set/inputs must be reconciled against it (plan Q15/Q19) — cheap: compare `Project.FilePath`, TFM, `Documents` vs discovered `Compile` items, `MetadataReferences` vs evaluated `Reference`s, and surface mismatches as Indeterminate.
  - *Restore grant*: MSBuildWorkspace does not restore; tethys decides whether to run restore before invoking it (and on Linux, packages.config cannot be restored at all — section C4).
  - *Analyzer/generator grants*: `Project.GetCompilationAsync()` runs source generators from the project's analyzer references **[inferred from Roslyn's CompilationTracker; not exercised — the fixture has no generators]**; without the generator grant strip `AnalyzerReferences` (`Solution.WithProjectAnalyzerReferences(id, [])`) before requesting compilations, and never call `GetSourceGeneratedDocumentsAsync`.
  - *No silent downgrade / provenance*: every `WorkspaceFailed` diagnostic (Failure ⇒ unit Indeterminate with the native MSB code; the Mono-fallback Warning ⇒ recorded host provenance `netcore-fallback`) plus `Project.OutputFilePath`, references, `ParseOptions.PreprocessorSymbolNames`, Roslyn/SDK versions go into the unit's provenance. Trivially available.
  - *Evaluation-unit identity*: still tethys-owned; the sidecar keys its JSONL by discovered unit id after reconciliation.
  - *Security qualification*: identical to Option 1 — design-time targets are arbitrary project code; BuildHost is a separate process but not a sandbox.
- **Risks**: Roslyn package/SDK version coupling (pin `Microsoft.CodeAnalysis.Workspaces.MSBuild` to the SDK band; BuildHost relaunches under the SDK's `dotnet`); Roslyn's diagnostics are strings, not typed (parse MSB/NETSDK/NU codes); roslyn#82931-style host regressions on Windows with new VS versions.

### Option 3 — complog / binlog ingestion (complements 1 or 2)

- **Demonstrated**: 27 lines rebuilt both compilations from a `.complog` produced by the user's own `dotnet build -bl`, with references, generated-file policy, and cross-language binding intact. For the target repo — built on Windows anyway — a CI leg running `complog create msbuild.binlog` (or `complog-action`) yields a portable artifact tethys can ingest on Linux with **no MSBuild, no targets, no restore, no generators executed by tethys** and *exact* inputs/provenance (compiler args, references, options, `TargetFramework` when present).
- **Mapping to the plan**: this is the "explicit source/options/references" stage with the acquisition stage delegated to the user's build. Grants collapse to one: "trust this build artifact" (it contains binaries; load with `BasicAnalyzerKind.None`). Identity: `CompilerCall.ProjectFilePath` (+ `TargetFramework`, null for classic → use `TargetFrameworkVersion` from the args/`-define`s) reconciled against discovery. Standing: units absent from the log are Indeterminate (`compiler-inputs-missing`); staleness = log older than sources → Indeterminate unless re-supplied. Same walker as Options 1/2.
- **Limits**: requires a *full* build (incremental binlogs omit up-to-date projects — observed: first binlog contained only csc); the user must run `complog create` on the build machine; `.complog` files embed source and references (treat as sensitive, keep out of git); complog is a one-maintainer project (Roslyn compiler team member; 41 stars) — pin the `Basic.CompilerLog.Util` version and keep a fallback to raw binlog reading (`BinaryLogReader` in the same package).

### Not viable as the primary route

- scip-dotnet output ingestion: loses identity (ordinal disambiguators, index-local packages), enclosing attribution, dispatch/accessor semantics, generated inputs; requires the same host workarounds anyway. Keep as an *oracle* for occurrences and `is_implementation` relationships (cheap: `scip print --json`).
- Roslyn LSIF generator: removed upstream.
- CodeQL: licence and monolithic-compilation model.

## Recommendation

**Yes — there are easier ways, and they keep every non-negotiable of the approved plan.** Replace the tethys-owned *acquisition* stage with the two acquisition paths that already exist and are verified to work on Linux for the target repo's project shapes, and keep only what is tethys-specific (identity, grants, provenance, standing, the semantic walker, Rust ingestion):

1. **Semantic engine = a pinned .NET sidecar built on `Microsoft.CodeAnalysis.Workspaces.MSBuild` (BuildHost), not a hand-rolled MSBuild adapter + raw `CSharpCompilation`.** Start it only under the design-time-target grant; pass tethys's recorded evaluation context as global properties; strip analyzer references unless the generator grant is present; reconcile its projects/inputs against evaluation-only discovery; map `WorkspaceFailed` Failures to per-unit Indeterminate with native codes and record host fallbacks as provenance. Emit JSONL keyed by `(unit_id, doc_comment_id)` with declarations, references (selected member, substitutions, accessor effect), direct calls, overrides/implementations, possible-dispatch candidates. Estimated saving vs the approved plan: the entire adapter/host-matrix (~1.5–3 k LOC and the riskiest qualification work); everything else is common cost.
2. **Add `complog`/binlog ingestion as the zero-execution path** for repositories that already build in CI (this target repo). Same walker, same JSONL, no grants beyond artifact trust, exact provenance. For a Windows-built Web Forms solution this is the *only* route that needs no host workarounds at all.
3. **Define the "classic .NET Framework on Linux" profile as data, not code**: `VSToolsPath=` (or a stub directory) + `Microsoft.NETFramework.ReferenceAssemblies.<tfm>` targets via `CustomAfterMicrosoftCommonTargets` + `FrameworkPathOverride`. Fail closed with `toolchain-unavailable`/`restore-required` when `packages/` is absent — `packages.config` cannot be restored by the dotnet CLI and Mono is end-of-life.
4. **Amend the VB rule** to "VB units are semantic inputs (skeleton/assembly metadata), not indexed sources". Without this, no C# project in the target repo that references a vbproj can be Confirmed. MSBuildWorkspace and complog provide it automatically; a direct-Roslyn design needs a metadata-only emit of a `VisualBasicCompilation` (verified, ~15 lines).
5. **Adopt documentation-comment IDs as the canonical symbol identity**, assembly/unit-qualified, with synthesised document-local IDs for lambdas, local functions, locals and parameters (Roslyn's own IDs collide for local functions — verified).
6. **Keep scip-dotnet only as an oracle** (occurrence and implementation-relationship cross-check); do not plan around the Roslyn LSIF generator or CodeQL.

What does *not* get easier: grants and their enforcement, evaluation-unit identity, provenance/reconciliation, Confirmed/Indeterminate standing, the semantic walker itself, and the Rust ingestion — those are tethys's actual product and are the same under every option.
