## Validated / learned

- P1: **Learning** — fresh execution includes roughly 61–80ms linked setup and 125–205ms evaluator work in the six-call sample; repeated-process speedup cannot be attributed solely to process creation.
- P2: **Learning** — disposal of ProjectCollection does not reset process environment state. One native counterexample is sufficient to reject universal resident-worker equivalence.
- P3: **Learning** — the provisional-to-authoritative byte-proof window is load-bearing. A returned import path and equal final size/mtime cannot replace it.
- P5: **Validated prior understanding** — independent, prepared project evaluations scale on this host; all measured native property/Compile outputs agree. This says nothing about general project side effects, Restore coordination, full-suite deadlines or worst-case memory.
- P6: **Learning** — warming core types without loading a user project preserves the measured serial metadata but yields only modest throughput improvement. It does not establish a repair for the failed scale gates.
- P7: **Learning** — shared filesystem side effects remain observable across fresh processes. Unconditional project concurrency changes existing serial execution behavior and therefore requires an explicit behavior/risk decision, not merely a placement decision.
- P8: **Learning** — profiling did not find a large removable bookkeeping phase. Native LoadProject dominates the evaluator body; skipping logical/recipe evidence would change observable output for only about 5ms per inner call. Independent native profiling attributes substantial time to property/import and target-definition evaluation, not companion cache reporting.
- P9: **Learning** — `target/qualification/venv/bin/python .tethys-82a6/probe-warm-repeat.py` returned zero using the retained release binary and exact same canonical workspace, with a fresh index. All 240 projects/401 units and complete discovery output matched. The original index was restored after retaining the repeated index separately. Discovery increased from 532.551s to 884.510s; the cause of the timing variation is not established. This rules out assuming a beneficial warm-run effect, not serial feasibility under the correctly assigned full cadence. The report retains binary hash, inputs, environment, output and phase frames. Its incomplete RSS sampling cannot satisfy a qualification resource gate.

P1–P9 are discharged as diagnostic evidence, not qualification acceptance. The fast candidate changes cross-project execution order (P7), and neither result-publication ordering nor Restore epochs can repair arbitrary evaluation-time side effects already observed in the wrong order. That candidate requires explicit risk acceptance if pursued. Correct cadence assignment is a separate Main-owned orchestration correction; it does not require that ordering waiver. No production performance implementation, calibrated baseline or design approval is recorded here.
