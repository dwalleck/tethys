C# project and evaluation-unit explorer

Throwaway decision prototype — not tethys behavior. Does separating a physical indexed file from its participation in each project × target framework preserve distinct bindings and partial evaluation evidence? This uses invented fixture facts, not MSBuild or Roslyn results.

Day-one release gate: SDK-style and classic non-SDK .NET Framework projects must both work. The framework identity is not restricted to the SDK's TargetFramework property: classic projects use evaluated identifier/version/profile or moniker. Real Windows MSBuild success is required; this browser fixture is not host qualification.

Approved: one active evaluation context; projects keyed by workspace-relative path; moves remove the old project identity; an evaluation unit is project × framework; semantic facts belong to that unit, while physical file identity is shared. Assemblies are metadata, never keys. Actions illustrate approved outcomes; this fixture does not implement transactional publication or a discovery provider.

Approved discovery seam

Approved flow: language-neutral discovery request → Cargo/MSBuild discovery adapters → metadata snapshot → index writer and context-aware extraction/reference resolution.

The snapshot describes project identities, evaluation units, source membership, evaluated references, assembly metadata, recorded context, and typed evaluation failures. It does not contain resolved symbol bindings. MSBuild execution stays outside ModuleResolver; ModuleResolver remains database-free. Successful and failed units publish as one coherent revision; concrete Rust types and persistence machinery are implementation work.

Rejected placement: attach discovery to LanguageSupport. Fewer registration points, but syntax extraction would share an interface and lifecycle with trusted external-process evaluation.
