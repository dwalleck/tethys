# C# binding semantic host research

Planning evidence for **Choose C# reference and binding semantics for parity**. Captured 2026-09-06. No project loaders, builds, restore, generators, or compiler probes were executed by this research. Official API/source review, not runtime qualification. Upstream `main`/`master` source links are moving references and must be pinned during implementation qualification.

## Maintainer-selected interpretation

Compiler-backed semantics is the parity-qualified path; no-host syntax/native results remain explicitly limited. Use separate out-of-process compiler-input acquisition and direct Roslyn semantics. Discovery remains evaluation-only and authoritative for project/evaluation-unit identity. Acquisition may execute design-time targets only under an explicit grant. Semantic mode, project-target execution, restore, generators and analyzers have separate recorded grants. Queries start no hosts.

Evaluation-only discovery does NOT, by itself, guarantee fully resolved compiler inputs or framework target selection. The acquisition stage must supply that evidence and reconcile exact context. Evaluated source membership and provenanced derived compiler/generated inputs remain distinct. Direct Roslyn APIs do not negotiate project-reference frameworks or discover missing inputs.

Out-of-process is not a security sandbox. MSBuild target execution is arbitrary project-controlled code: capability separation must not be represented as a guaranteed barrier against a malicious target doing network/restore/plugin work. Host containment/enforcement and real SDK/classic Framework qualification remain implementation acceptance obligations. Research recommendations below are evidence, not additional maintainer approvals.

## Direct compiler API investigation

## Facts from primary sources

### Direct construction and semantic scope
* `CSharpCompilation.Create` accepts only a simple assembly name, `IEnumerable<SyntaxTree>`, `IEnumerable<MetadataReference>`, and `CSharpCompilationOptions`; it creates a compilation from scratch. It has no project path, item glob, MSBuild evaluator, package restore, target-framework selector, generator list, or analyzer list input ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation.create?view=roslyn-dotnet-5.3.0)).
* `CSharpCompilation` is an immutable representation of one compiler invocation and is explicitly described as **on-demand**, realizing/caching data as needed ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation?view=roslyn-dotnet-5.3.0)). Construction can therefore be cheap; `GetDiagnostics`, `GetSemanticModel`, symbol lookup, and related queries trigger compiler work. `GetDiagnostics` covers syntax, declarations, and binding, but not emit diagnostics ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation.getdiagnostics?view=roslyn-dotnet-5.3.0)).
* Source membership is not discovered. The host must supply every intended source as text (or `SourceText`) and logical path, parse each with `CSharpSyntaxTree.ParseText`, and add the resulting trees ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpsyntaxtree.parsetext?view=roslyn-dotnet-5.3.0)). `CSharpParseOptions.LanguageVersion` selects the language rules used by the compiler ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpparseoptions.languageversion?view=roslyn-dotnet-5.3.0)); the host must also carry per-project/per-file preprocessor symbols, documentation mode, source kind, and any syntax-tree-specific options.
* `CSharpCompilationOptions` controls output kind, optimization, platform, unsafe code, nullable context, global usings, warning/diagnostic policies, metadata/source/XML resolvers, and related compiler behavior ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilationoptions?view=roslyn-dotnet-5.3.0)). These are required parity inputs, not defaults to infer from a project file at this layer.

### Metadata and project references
* `MetadataReference.CreateFromFile` creates a reference to an assembly or standalone module, reads the entire file into memory, and accepts aliases/embed-interop/image-kind properties ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.metadatareference.createfromfile?view=roslyn-dotnet-5.3.0)). For repeated references to the same image, Microsoft recommends `AssemblyMetadata.CreateFromFile` and `GetReference` so metadata can be shared ([AssemblyMetadata API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.assemblymetadata?view=roslyn-dotnet-5.3.0), [GetReference](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.assemblymetadata.getreference?view=roslyn-dotnet-5.3.0)). In-memory alternatives are exposed by `MetadataReference` (`CreateFromImage`/`CreateFromStream`) ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.metadatareference?view=roslyn-dotnet-5.3.0)).
* A `MetadataReference` is a logical location; its content snapshot is taken when the compiler queries metadata. `Display` is only a path/name for diagnostics, not assembly identity. `MetadataReferenceProperties` carries aliases, embed-interop, and assembly/module image kind ([MetadataReference](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.metadatareference?view=roslyn-dotnet-5.3.0), [properties](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.metadatareferenceproperties?view=roslyn-dotnet-5.3.0)).
* For reference-target proof, retain the exact `MetadataReference` object, call `Compilation.GetAssemblyOrModuleSymbol(reference)` (returns the corresponding `IAssemblySymbol`/`IModuleSymbol`, or null), and for an assembly inspect `IAssemblySymbol.Identity` ([GetAssemblyOrModuleSymbol](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.compilation.getassemblyormodulesymbol?view=roslyn-dotnet-5.3.0), [Identity](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.iassemblysymbol.identity?view=roslyn-dotnet-5.3.0)). `AssemblyIdentity` is CLI metadata identity and exposes simple name, version, culture, public key/token, content type, strong-name/retargetable flags, and equality/display operations ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.assemblyidentity?view=roslyn-dotnet-5.3.0)). This proves the consumed metadata image’s assembly identity; it does **not**, by itself, prove the selected TFM or that the image was the project-reference output intended by evaluation. Keep TFM/output/reference-assembly proof as separate trusted facts.
* `CompilationReference` is a separate explicit Roslyn reference to another C#/VB `Compilation` ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.compilationreference?view=roslyn-dotnet-5.3.0)). It is appropriate only if the host intentionally builds a project graph in memory and can establish that child compilation’s options/references/TFM match the evaluated unit. For parity with an evaluated project output, a `PortableExecutableReference` to the exact evaluated output/reference assembly is the less ambiguous representation.
* For unique-or-decline selection, `GetTypeByMetadataName` searches source/core/reference assemblies and returns null when not found **or ambiguous**; its docs explicitly say ambiguity is detected across matching referenced assemblies. `GetTypesByMetadataName` returns every matching symbol, allowing a caller to apply a declared policy ([unique lookup](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.compilation.gettypebymetadataname?view=roslyn-dotnet-5.3.0), [all matches](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.compilation.gettypesbymetadataname?view=roslyn-dotnet-5.3.0)).

### Generators, analyzers, and execution/consent
* Generators are not automatic in `CSharpCompilation.Create`. `CSharpGeneratorDriver.Create` takes explicit generator instances (plus parse options, additional texts, config provider, and driver options), and `RunGeneratorsAndUpdateCompilation` is the explicit call that returns a generated-source-updated compilation and generator diagnostics ([driver](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpgeneratordriver?view=roslyn-dotnet-5.3.0), [run/update](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.generatordriver.rungeneratorsandupdatecompilation?view=roslyn-dotnet-5.3.0)). `GeneratorExecutionContext.Compilation` contains only user-supplied code; generated code is not available in that input compilation ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.generatorexecutioncontext.compilation?view=roslyn-dotnet-5.3.0)).
* Analyzers are likewise explicit: `Compilation.WithAnalyzers` attaches a supplied analyzer array and returns `CompilationWithAnalyzers`; `GetAnalyzerDiagnosticsAsync` then obtains analyzer diagnostics ([WithAnalyzers](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.diagnostics.diagnosticanalyzerextensions.withanalyzers?view=roslyn-dotnet-5.3.0), [diagnostics](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.diagnostics.compilationwithanalyzers.getanalyzerdiagnosticsasync?view=roslyn-dotnet-5.3.0)).
* Therefore direct construction, parsing, metadata reading, binding, diagnostics, and semantic-model queries do not build/restore/load/execute target project code. They execute Roslyn’s own compiler/metadata algorithms and perform file/stream reads. `Compilation.Emit` is also an explicit operation that writes IL to a stream, not execution of that IL ([Emit](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.compilation.emit?view=roslyn-dotnet-5.3.0)). Explicit generator/analyzer invocation is a different boundary: it executes supplied tool assemblies as host code and must be separately opt-in/consented, isolated as appropriate, and given exact additional texts, analyzer config, parse/compilation options, and tool assemblies if parity is required. The Roslyn SDK characterizes analyzers as static analysis and says they do not run the analyzed program ([SDK](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/)).

### Classic non-SDK .NET Framework constraints
* Microsoft’s reference-assembly guidance says reference assemblies contain the public API metadata needed by compilers, cannot be loaded for execution, and—critically—when using the C# command line or Roslyn `Compilation.AddReferences`, the caller must manually specify the reference-assembly files for the correct target platform/framework version ([reference assemblies](https://learn.microsoft.com/en-us/dotnet/standard/assembly/reference-assemblies)).
* A .NET Framework developer/targeting pack supplies that framework’s reference assemblies; using reference assemblies avoids accidentally binding to a newer implementation API. If the matching pack cannot be installed, Microsoft documents `Microsoft.NETFramework.ReferenceAssemblies`, whose selected reference set is controlled by `TargetFrameworkVersion`/`TargetFramework` and which must be restored ([targeting packs](https://learn.microsoft.com/en-us/dotnet/framework/install/guide-for-developers), [reference package](https://learn.microsoft.com/en-us/dotnet/framework/migration-guide/reference-assemblies)).
* `Microsoft.CodeAnalysis.CSharp` 5.9.0 publishes a `netstandard2.0` compiler asset ([NuGet](https://www.nuget.org/packages/Microsoft.CodeAnalysis.CSharp/5.9.0)). Thus a host can analyze classic Framework source when it has the exact Framework reference assemblies and all other metadata inputs; Roslyn direct APIs do not locate/install/restore those inputs. This is a host/package compatibility statement, not a claim that a reference assembly is executable.

### MSBuild framework-selection proof (comparison path)
* The official MSBuild `ProjectReference` protocol says common targets transform `ProjectReference` items into compiler references. `PrepareProjectReferences` verifies existence; `_ComputeProjectReferenceTargetFrameworkMatches` invokes referenced projects’ `GetTargetFrameworks`; NuGet’s `GetReferenceNearestTargetFrameworkTask` selects the closest compatible framework; `GetTargetPath` returns a project output without building; default project-reference targets build and return outputs ([protocol](https://raw.githubusercontent.com/dotnet/msbuild/main/documentation/ProjectReference-Protocol.md)). `GetTargetFrameworks` metadata includes available `TargetFrameworks`, `TargetFrameworkMonikers`, `TargetPlatformMonikers`, `HasSingleTargetFramework`, and `IsRidAgnostic`.
* The common-target implementation calls `GetTargetFrameworks`, invokes `GetReferenceNearestTargetFrameworkTask`, and, for a multi-targeted reference, writes `SetTargetFramework=TargetFramework=%(NearestTargetFramework)`; single-target references have `TargetFramework` undefined to avoid a second evaluation ([official source](https://raw.githubusercontent.com/dotnet/msbuild/main/src/Tasks/Microsoft.Common.CurrentVersion.targets), sections `_GetProjectReferenceTargetFrameworkProperties`, approximately lines 1779–2063). `ResolveProjectReferences` then either calls `GetTargetPath` (IDE/design-time or `BuildProjectReferences=false`) or invokes the referenced target/build and collects `_ResolvedProjectReferencePaths` with `SetTargetFramework` passed through (same source, approximately lines 2119–2208). `GetTargetPathWithTargetPlatformMoniker` carries `TargetFrameworkIdentifier`, `TargetFrameworkVersion`, target platform metadata, and optional `ReferenceAssembly` (same source, approximately lines 2255–2301).
* For `TargetFrameworks` projects, the cross-targeting targets normalize each framework and dispatch inner builds with `TargetFramework=<value>` ([official source](https://raw.githubusercontent.com/dotnet/msbuild/main/src/Tasks/Microsoft.Common.CrossTargeting.targets), `_ComputeTargetFrameworkItems`/`DispatchToInnerBuilds`). This framework negotiation and project-output production are outside direct Roslyn compilation. The evaluator must provide the selected TFM/platform, selected project-reference output or reference assembly path, and the evidence tying that output to the selected evaluation unit. An assembly identity check alone is insufficient.

## Required pre-evaluated input contract
1. Exact compile source membership after project conditions/globs/Remove/Update, source bytes/text, logical paths, and any already-produced/generated source that is intentionally part of the unit.
2. Exact `CSharpParseOptions` (language version, preprocessor symbols, documentation mode, source kind, per-file overrides).
3. Exact `CSharpCompilationOptions` (assembly/module name, output kind, platform, optimization, unsafe, nullable, global usings, warning policies, deterministic/signing options, and resolvers when source directives/includes are permitted).
4. Exact metadata/project references: framework reference assemblies, package assets, project output/reference-assembly paths, transitive dependencies, aliases, embed-interop/image kind, and expected assembly identities. Do not infer these from the running host’s loaded assemblies or from filenames.
5. Trusted evaluation facts separate from Roslyn symbols: project identity, configuration/platform, selected target framework/platform, nearest-framework decision, output/reference assembly path, and any target-framework compatibility/decline reason.
6. If explicit analyzers/generators are eventually enabled: tool assembly identities/paths, analyzer config, additional texts, generator/analyzer options, and an explicit consent/isolation policy. Otherwise decline projects whose semantic parity depends on generation/analyzer execution rather than silently executing them.

## Limits and unresolved qualification
* Direct Roslyn construction gives compile-time syntax/binding/semantic facts. Runtime method dispatch, reflection behavior, loader probing, binding redirects, and runtime type identity are not executed or proven by the compilation; they remain a separate runtime concern.
* Roslyn metadata identity proves the selected image’s CLI assembly identity, while MSBuild target-framework metadata proves evaluation selection. Neither alone proves all runtime compatibility or deployment behavior.
* `MSBuildWorkspace` is an optional project-loader path, not required by direct construction. Its package is explicitly for analyzing MSBuild projects/solutions ([NuGet](https://www.nuget.org/packages/Microsoft.CodeAnalysis.Workspaces.MSBuild/5.9.0)); using it would reintroduce MSBuild/project loading and its framework/toolchain behavior, contrary to the direct host’s explicit-input boundary.

## Project-loader and LSP investigation

## Findings and limits

### 1. Roslyn MSBuildWorkspace is a design-time build, not a read-only project parser

`MSBuildWorkspace.Create(properties)` forwards properties as global MSBuild properties. Its loader starts an out-of-process BuildHost, evaluates the project, then requests project information and constructs Roslyn `ProjectInfo` objects containing documents, project/metadata references, analyzer references, analyzer-config documents, parse options, and compilation options ([MSBuildWorkspace.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/Core/MSBuild/MSBuildWorkspace.cs), [MSBuildProjectLoader.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/Core/MSBuild/MSBuildProjectLoader.cs), [BuildHostProjectFileInfoProvider.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/Core/MSBuild/BuildHostProjectFileInfoProvider.cs), [MSBuildProjectLoader.Worker.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/Core/MSBuild/MSBuildProjectLoader.Worker.cs)).

The current Roslyn `ProjectBuildManager` sets `DesignTimeBuild=true`, `BuildProjectReferences=false`, `BuildingProject=false`, `ProvideCommandLineArgs=true`, and `SkipCompilerExecution=true` by default. It evaluates with project-load safeguards, then executes required `Compile` and `CoreCompile` targets (and optional design-time markup compilation) to obtain the post-target project state ([ProjectBuildManager.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/BuildHost/Build/ProjectBuildManager.cs)). Therefore “design-time” means no normal compiler/output build, not “no target/task execution.”

Microsoft’s project-system documentation confirms that design-time builds invoke additional targets such as `ResolveAssemblyReferencesDesignTime`, `ResolveProjectReferencesDesignTime2`, `ResolveFrameworkReferencesDesignTime`, `ResolvePackageDependenciesDesignTime`, `CollectAnalyzersDesignTime`, and `CompileDesignTime`; multi-target projects receive a separate design-time build for each TFM ([design-time-builds.md](https://raw.githubusercontent.com/dotnet/project-system/main/docs/design-time-builds.md)). MSBuild’s evaluation processes imported props/targets and `UsingTask` declarations, while execution runs targets and tasks ([MSBuild build process](https://learn.microsoft.com/en-us/visualstudio/msbuild/build-process-overview?view=visualstudio)).

### 2. Explicit capability consent is required

Microsoft explicitly advises running MSBuild for building, restoring, and opening projects only on trusted/reviewed sources; unknown MSBuild logic should be assumed capable of arbitrary code. Imports may come from project/solution files, `Directory.Build.*`, user extensions, and before/after targets. NuGet `build`, `buildTransitive`, `buildMultitargeting`, and `analyzers` assets can extend execution ([Secure MSBuild usage](https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild-security-best-practices?view=visualstudio)).

Recommended controls:

* Require a distinct user grant before project evaluation/design-time execution; no-host mode remains the safe default.
* Grant restore separately. Restore may access feeds/network and write `obj/project.assets.json` and generated imports. Do not infer that MSBuildWorkspace performs or is authorized to perform restore.
* Grant analyzers/source generators separately from project loading; they are executable compiler extensions.
* Run the BuildHost with timeout/cancellation, constrained environment, filesystem/network policy, and low-privilege isolation. Out-of-process BuildHost is an isolation boundary for failure/runtime selection, not a security boundary by itself.
* Record project/import/package/tool/SDK/MSBuild provenance and all diagnostics. A warning, fallback host, missing target, or failed generator invalidates a full-fidelity claim rather than silently degrading.

OmniSharp demonstrates the useful consent split: `EnablePackageAutoRestore` is a separate option, and `PackageDependencyChecker` invokes `RestoreAsync` only when dependencies are unresolved and both the queue’s `allowAutoRestore` and the option are true; otherwise it reports unresolved dependencies ([MSBuildOptions.cs](https://raw.githubusercontent.com/OmniSharp/omnisharp-roslyn/master/src/OmniSharp.MSBuild/Options/MSBuildOptions.cs), [PackageDependencyChecker.cs](https://raw.githubusercontent.com/OmniSharp/omnisharp-roslyn/master/src/OmniSharp.MSBuild/PackageDependencyChecker.cs)).

### 3. Restore/assets and generated inputs are qualification obligations

NuGet writes `obj/project.assets.json`, which the SDK consumes for package/compiler information. If assets lacks the selected TFM, the SDK reports NETSDK1005/1047; the documented remedy is matching restore with compatible tooling ([NETSDK1005](https://learn.microsoft.com/en-us/dotnet/core/tools/sdk-errors/netsdk1005)). A semantic result must therefore be tied to the exact assets/restore state for its TFM, not merely to the project path.

Roslyn carries `ProjectAssetsFilePath`, exact `TargetFramework`, `TargetFrameworkIdentifier/Version`, references, analyzer config files, package references, and compiler command-line arguments out of the post-target ProjectInstance ([ProjectFile.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/BuildHost/MSBuild/ProjectFile/ProjectFile.cs), [ProjectInstanceReader.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/BuildHost/MSBuild/ProjectFile/ProjectInstanceReader.cs)). These should be retained as evaluation-unit provenance.

Source generators are compiler-time metaprogramming added to a compilation and may consume additional files ([Roslyn SDK](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/)). They are not equivalent to ordinary MSBuild `Compile` files, and generated source is commonly in memory unless explicitly emitted. Generator/analyzer availability, compatibility, diagnostics, and output must be checked per evaluation unit.

### 4. Framework/host fidelity is not established by project syntax alone

Current Roslyn BuildHost selection inspects project XML: SDK markers or `TargetFramework(s)` select a .NET host; otherwise Windows selects a .NET Framework host and non-Windows selects Mono. It can fall back from unavailable Mono/.NET Framework hosts to .NET Core with a warning that errors may occur; the manager may relaunch a .NET host using the SDK’s own `dotnet` executable ([BuildHostProcessManager.cs](https://raw.githubusercontent.com/dotnet/roslyn/main/src/Workspaces/MSBuild/Core/MSBuild/BuildHostProcessManager.cs)). Host kind, selected SDK/MSBuild path, fallback status, and target packs are therefore mandatory provenance—not assumptions.

OmniSharp documents separate `net6.0` and `net472` server builds because in-process MSBuild required a .NET Framework host for older Framework projects/Mono and a .NET host for SDK projects; its proposal to move project loading out of process is not proof that every legacy project is supported ([OmniSharp README](https://raw.githubusercontent.com/OmniSharp/omnisharp-roslyn/master/README.md), [issue #2647](https://github.com/OmniSharp/omnisharp-roslyn/issues/2647)). Traditional projects use `TargetFrameworkVersion` and explicit `Microsoft.CSharp.targets`, while SDK-style projects use `TargetFramework` (for example `net472`) ([framework overview](https://learn.microsoft.com/en-us/dotnet/core/porting/framework-overview), [project-system opening guidance](https://raw.githubusercontent.com/dotnet/project-system/main/docs/opening-with-new-project-system.md)). Legacy non-SDK .NET Framework support must remain a qualified host path; it must not be declared supported from an XML classification or fallback alone.

OmniSharp’s loader sets design-time globals, executes `Compile`/`CoreCompile`, and when `TargetFrameworks` is present without a selected `TargetFramework`, chooses the first framework ([ProjectLoader.cs](https://raw.githubusercontent.com/OmniSharp/omnisharp-roslyn/master/src/OmniSharp.MSBuild/ProjectLoader.cs)). csharp-ls instead computes a normalized common TFM intersection, sets global `TargetFramework`, and enables metadata for referenced projects; its source comments explicitly warn that a globally selected TFM absent from a project’s restored assets causes NETSDK1005 and loses package/framework references ([Solution.fs](https://raw.githubusercontent.com/razzmatazz/csharp-language-server/main/src/CSharpLanguageServer/Roslyn/Solution.fs)). Neither “first TFM” nor “common TFM” should be adopted as an authoritative decision for Tethys. Load each required TFM or decline when the requested unit cannot be proven.

### 5. LSP locations cannot prove exact unit, overload, or context

LSP `Location` contains only `{ uri, range }` ([Location](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/location.md)). `textDocument/definition` returns `Location`, `Location[]`, `LocationLink[]`, or null ([definition request](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/language/definition.md)); `LocationLink` only adds origin/target ranges and target URI ([LocationLink](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/locationLink.md)). None carries the Roslyn symbol, project, TFM, assembly identity, overload signature, or compile-time context.

csharp-ls resolves a Roslyn symbol but then its definition handler returns mapped locations; source locations become ordinary URI/range values, metadata may be decompiled/approximated, and generated locations use `csharp:/<project.csproj>/generated/<hint>` ([Definition.fs](https://raw.githubusercontent.com/razzmatazz/csharp-language-server/main/src/CSharpLanguageServer/Handlers/Definition.fs), [WorkspaceFolder.fs](https://raw.githubusercontent.com/razzmatazz/csharp-language-server/main/src/CSharpLanguageServer/Lsp/WorkspaceFolder.fs)). Its generated URI lacks a TFM, and its metadata handler finds a project by matching project path and then a matching hint name, so same-path multi-TFM flavors are not independently identified ([CSharpMetadata.fs](https://raw.githubusercontent.com/razzmatazz/csharp-language-server/main/src/CSharpLanguageServer/Handlers/CSharpMetadata.fs)). csharp-ls’s standard Moniker provider is currently unimplemented ([Moniker.fs](https://raw.githubusercontent.com/razzmatazz/csharp-language-server/main/src/CSharpLanguageServer/Handlers/Moniker.fs)).

Roslyn `ISymbol` is the authoritative layer: it exposes containing assembly/module/symbol, `OriginalDefinition`, `IsDefinition`, metadata name/token, equality, and source/metadata `Locations` (which may be multiple for partial symbols) ([ISymbol API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.isymbol?view=roslyn-dotnet-5.3.0)). Preserve this symbol identity and the semantic model/evaluation-unit provenance in the host. Treat LSP locations and virtual metadata URIs as navigation/presentation evidence only. If unique compile-time symbol selection or exact unit identity is unavailable, return decline; do not infer an overload or runtime dispatch from a location.

### Concrete decisions for Tethys

1. **Authority:** evaluated project/framework identity remains Tethys-owned and separately trusted; compiler-backed Roslyn is an opt-in semantic oracle for that exact unit, not the authority for discovery.
2. **Identity:** key every semantic result by project path, configuration/platform, exact TFM, SDK/MSBuild/host kind and path, assets/reference fingerprint, and analyzer/generator state. Never merge TFMs or accept host fallback silently.
3. **Capabilities:** separate grants for evaluation/DTB, restore/network/cache writes, analyzers, and source generators; retain an explicit no-host mode.
4. **Binding:** ask Roslyn for the compile-time selected symbol and retain a canonical binding identity (containing assembly/type chain, name, generic arity, parameter/ref signatures, and evaluation-unit ID). Apply unique-or-decline. Runtime virtual dispatch remains a separate concern.
5. **LSP:** use csharp-ls/OmniSharp only for explicit navigation or transport adapters. A returned location cannot establish exact overload, unit, assembly, TFM, or runtime context.
6. **Qualification:** mandatory smoke matrix must cover SDK and classic non-SDK Framework projects, multi-targeting, conditional imports/configurations, missing or stale assets, analyzers/generators, generated/decompiled locations, host fallback, and failed design-time targets. Unsupported or unproven cases must decline with diagnostics rather than be reported as supported.
